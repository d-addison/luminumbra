# Plugin integration synthesis

This synthesis ranks all 56 candidate integrations from the nine area reports. The order favors broad prerequisites and enforceable correctness contracts, then workflow accelerators, then specialized diagnostics, and finally deferred alternatives. Each placement balances the source report's effort and risk against leverage; a cheap candidate ranks lower when it preserves an inadequate interface, while a larger candidate can rank higher when several later integrations depend on it.

## Top 3

1. **Typed Banso steps and pipelines** — The [automation report](automation.md) calls this the canonical orchestration layer and rates it **M / low-to-medium** because the engine commands already exist. It has the broadest leverage: one typed supervisor, result contract, and run manifest can be reused instead of duplicating process semantics across later integrations.

2. **Banso `simulation` verification domain** — The [simulation report](simulation.md) rates this **very high value**, **3-5 days**, and **low-medium risk**, and recommends it first because it wraps rather than replaces the current deterministic gates. It is the strongest first consumer of the typed orchestration foundation and immediately protects the central `world_hash` contract.

3. **Bank contract validator** — The [audio report](audio.md) explicitly identifies this as the **highest-leverage, lowest-risk** audio candidate and rates it **S / low**. It turns silent runtime failures into precise preflight errors and establishes the prerequisite contract for every subsequent audio workflow.

## Roadmap

1. **Foundation — Typed Banso steps and pipelines.** Define the shared process supervisor, exact-argv construction, timeout/cancellation behavior, normalized result envelope, and run/artifact manifest. Prove semantic preservation with argv snapshots and result fixtures before adding domain wrappers.
2. **Independent contract lane — Bank contract validator.** Build the standalone validator against the current bank/decoder behavior, add fixtures for missing, duplicate, and undecodable assets, then expose the same command through a targeted typed preflight step. This lane depends only on the shared step contract for orchestration, not for validator correctness.
3. **Determinism lane — Banso `simulation` verification domain.** Compose the existing smoke, replay, lockstep, and targeted CTest entry points through named typed steps; preserve exact inputs and exit classifications; publish normalized hashes and failure evidence. This lane depends on the foundation's supervisor and manifests and can proceed in parallel with the validator once those interfaces freeze.
4. **Integration gate.** Run both domain lanes through the common manifest/result schema, verify that failures retain raw evidence, and require semantic parity with direct CLI invocations before either wrapper becomes a required gate.
