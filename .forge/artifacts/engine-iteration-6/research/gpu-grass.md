# GPU grass — continuous scene-lit cloud-shadowed turf

**Slug:** `gpu-grass` · **Side:** RENDER-only (no `world_hash` impact) · **Iteration:** 6, Wave 0
**Primary source:** *Procedural Grass in 'Ghost of Tsushima'*, Eric Wohllaib, GDC 2021 (Advanced Graphics Summit).

---

## Recommended approach

Replace the current CPU-built instanced-billboard `FoliagePass` with a **GPU-driven, compute-generated, indirect-drawn per-blade grass field** modelled on Sucker Punch's Ghost of Tsushima (GoT) system, adapted to luminumbra's existing tile/streaming and analytic-cloud infrastructure. Five stages:

1. **Density/parameter tiles (CPU → GPU, per-frame, cheap).** The current pass already iterates *visible chunks* and queries a `SurfaceQuery` for height/slope/moisture/validity, and reads the biome vegetation density `[0,1]` per chunk (`FoliagePass::ChunkScatter`). Keep that exact host-side input but stop emitting per-instance records on the CPU. Instead, upload a compact **per-tile parameter set** (chunk origin/extent, biome id, density, and a coarse height/slope/moisture sample grid for the chunk footprint) to a GPU buffer. GoT segments the world into tiles carrying terrain-height / material / grass-type / grass-height textures and subdivides them into render-friendly child tiles for efficient sampling [1][3]. luminumbra's 24 m FieldGrid cells and the chunk footprint are the natural tile grid; the per-chunk density we already compute becomes the GPU tile's density input.

2. **Compute blade layout + cull (GPU).** A compute shader runs one thread per **candidate blade slot** on a jittered grid inside each tile, samples the tile parameter textures, performs **frustum + distance culling in the shader**, and appends surviving blades' parameters to a `GrassBlades` SSBO; the CPU never touches individual blade data [1][2][3][4]. Reproduce the existing CPU placement contract on the GPU verbatim: the `splitmix64`/`hash_unit` jitter, the sea-level + slope hard gates (`kMaxFoliageSlope ≈ 0.70`, sea-level + 0.4 m margin), and the `density · 2.4 · slope² · moisture` accept threshold from `FoliagePass::rebuild_instances`. Because every term is a pure hash of (chunk x,z, biome, slot idx), the field stays deterministic *as a function of camera/world inputs* — the same render-only contract the pass already asserts.

3. **Indirect draw (GPU).** The compute stage writes the surviving blade count into an **indirect-args buffer** (`glDrawArraysIndirect` / `glMultiDrawArraysIndirect`); the draw consumes the `GrassBlades` SSBO with **no vertex streams** — the vertex shader indexes blade id into the SSBO and procedurally positions vertices [2][3]. This removes the per-frame `memcpy` of up to 262 144 × 36 B (≈9 MB) into the persistent-mapped ring that the current pass does every frame, and removes the CPU scatter loop entirely.

4. **Per-blade Bézier geometry + distance LOD.** Each blade is a **cubic Bézier curve** with artist params tilt / bend / facing; the vertex shader evaluates the curve [1][3][4]. Use GoT's three-tier LOD: near blades ~**15 verts**, far blades ~**7 verts**, and the *very-far* field replaced by a textured terrain layer [3]. At each LOD/tile boundary GoT **blends vertex positions for pop-free transitions** and **drops 3 of every 4 blades** when promoting to the larger (coarser) tile — the lower density is "less noticeable at distance" [1][3]. This is the density falloff that lets the field scale to luminumbra's **6× view distance**: keep full per-blade grass only inside the live-chunk ring (current `m_fade_start_m = 96 m`, `m_fade_end_m = 160 m`), apply the 4:1 thinning per tile-LOD step, and beyond the grass horizon hand off to a **terrain-texture grass layer baked into the G-buffer / FarLodStore tiles** (F1 = 4 m / 512–768 m, F2 = 8 m / 768–1536 m) rather than spawning blades — i.e. per-blade grass never reaches the 1536 m far field.

5. **Scene lighting + analytic cloud shadow.** The new pass must consume the **same lighting inputs the terrain lighting pass uses** so turf is continuous with the ground: sun direction/color/intensity, sky ambient, the Materials-LUT-driven emissive (`kEmissiveLutScale = 8.0`, row 2), and — critically — the **same analytic procedural cloud cast-shadow** the `LightingPass` projects. luminumbra's cloud shadow is **not a sampled shadow map**: `CloudRenderState` (RenderPipeline.h:148) is a coverage field re-projected analytically (scroll offset = wind·tick-phase, `coverage_amount`, `shadow_strength`, `sun_travel_dir`, `plane_height`), and the *current* foliage shader already replicates that exact projection (FoliagePass.cpp:454-466, uniforms `u_cloud*`). Carry those uniforms forward unchanged so blades darken under storm cells exactly like the terrain. GoT's grass receives global volumetric/cloud lighting from the scene and tilts blade normals outward, blending toward a clump normal at distance for stable specular [1][3]. Wind comes from the existing **FieldGrid wind field** (iter-5a, FieldGrid API frozen for iter-6): GoT uses scrolled 2D-noise global wind plus per-blade phase-offset sine bob [1][3][4]; feed the FieldGrid sampled wind vector (already bridged one-way into the pass via `set_wind`) as the global term and derive the per-blade phase from the blade hash.

**Net:** a one-pass replacement (`GrassPass` / rebuilt `FoliagePass`) inserted at the current foliage slot in the RenderPipeline order (… lighting → water → skybox → aerial-perspective → **grass** → particle → HDR blit), reading scene depth for occlusion exactly as today.

## Alternatives considered (and why rejected)

- **Keep CPU instanced billboards, just push density higher.** Current cap is 262 144 instances, 2048 candidates/chunk, rebuilt and `memcpy`'d on the CPU every frame. This is the *thing being replaced*: it cannot reach continuous turf at 6× view distance without an unaffordable CPU scatter cost and a multi-MB per-frame upload, and flat cross-quad cards are exactly what produced the GREEN_SKY_SPECKLE / cyan-glow defects the team has been firefighting (FoliagePass.cpp:362-377). Rejected — does not close the OPEN BLOCK.
- **Geometry/tessellation-shader blade generation.** Generate blades by tessellating a ground patch. Rejected: GoT, the Unity/Vulkan reference implementations, and the second-source benchmarks all converge on **compute + indirect-draw** as the scalable path with "zero CPU overhead" [1][2][6]; geometry-shader throughput is poor on the target class of GPU and harder to cull per-blade.
- **Mesh-shader pipeline.** Cleaner per-meshlet culling, but requires GL_NV_mesh_shader / a newer baseline than the rest of the GL renderer assumes, and the GPUSDFSystem compute path is still gated off (`kEnableExperimentalGpuSdfIntegration=false`) — adding a second bleeding-edge GPU path is risk the iteration can't absorb. Compute + indirect uses GL features already in the engine (it mirrors the disabled GPUSDF compute stubs). Rejected for iter-6.
- **Sampled cloud-shadow map (render clouds to a depth/coverage texture, sample it on grass).** Would diverge from how the terrain is actually shadowed. luminumbra uses an **analytic projection**, not a shadow texture; the grass must read the identical analytic state to stay registered with terrain. Rejected — would reintroduce the storm/teal mismatch the analytic path fixed.

## Perf budget (concrete GPU ms + VRAM)

The total iter-6 GPU budget is **shared and contended** across SHIELD-RT raymarch, GPU grass, and volumetric clouds (and Aetheric field sampling). Proposed **grass split: ≤ 2.0 ms GPU and ≤ 40 MB VRAM** at the live-ring blade counts below. Justification, pinned to measurement:

- **Second-source benchmark (RX 5600 XT, 1080p)** [6]: ~6.77 M blades all-visible → compute ≈ **4.7 ms**, draw ≈ **8 ms**; a 1000×1000 layout up to 19 M blades → compute ≈ **2.5 ms**, draw ≈ **6 ms**. These are *brute-force, all-visible, no-LOD* numbers and set the worst case.
- luminumbra does **not** need millions of full-detail blades visible: the live grass ring is ~160 m, and the 4:1 per-LOD thinning plus terrain-texture handoff caps the full-detail blade set far below those benchmarks. Target a working set of **~1.0–1.5 M visible blades** inside the live ring. Scaling the benchmark linearly (≈0.7 ms compute + ≈1.2 ms draw per ~6.77 M → for ~1.3 M): **compute ≈ 0.3 ms, draw ≈ 0.7 ms, ≈ 1.0 ms typical**, with **≤ 2.0 ms** headroom for windy/dense storm cells. This is the figure Wave A should reserve.
- **VRAM:** `GrassBlades` SSBO at a generous packed stride (~32 B: pos + tilt/bend/facing + hue/height params) × 1.5 M live blades ≈ **48 MB** worst case; trim to **≤ 32 MB** by (a) capping the live ring count and (b) *not passing per-blade vertex data* to the VS — a documented saving of "hundreds of MB" [6]. Indirect-args + per-tile param buffers are kilobytes. Add the **40 MB grass cap to the shared GPU budget alongside SHIELD-RT and clouds** (FarLodStore already owns its own 64 MB residency budget — grass does not touch it except to write the far-field texture-grass layer).
- This *removes* the current per-frame CPU cost: up to 262 144-iteration scatter loop + up to ~9 MB `memcpy` into the persistent ring, every frame.

> **Flagged / unverified:** the GoT talk's *own* PS4/PS5 grass ms and memory figures were not recoverable from the secondary write-ups (slides/video behind GDC Vault). The companion SIGGRAPH 2021 "Real-Time Samurai Cinema" talk gives *non-grass* PS4 figures (volumetric haze ≈ 0.5 ms, 768×768 cloud paraboloid) [5] but no grass timing. The ms/VRAM above are derived from a **third-party RX 5600 XT benchmark** [6] scaled to luminumbra's ring, not from Sucker Punch's shipped numbers — treat as an engineering estimate to be re-measured against the engine's per-pass GL timestamp timers on the project's quiet-machine baseline.

## Determinism implications (sim vs render; world_hash impact)

**RENDER-only. No `world_hash` impact. No deliberate bump, no re-bless.** Grass is generated each frame from a pure hash of render/world inputs and never written back into any sim state — identical to the existing `FoliagePass` one-way contract (FoliagePass.h:42-46). Specific points:

- The compute placement must reproduce the current pure-function placement (`placement_hash` = chained `splitmix64` over chunk x,z / biome / slot idx) so the field is reproducible from the same inputs. GLSL has no `splitmix64` intrinsic, so port the exact 64-bit integer mixer into the compute shader; integer ops are bit-exact across GPUs, so the *placement* hash stays stable. **Float blade params (Bézier, wind, color) are render-side and need not be bit-exact** — they never feed `world_hash`.
- This pass uses GPU `libm`-equivalent transcendentals and atomic-append (unordered) — **all forbidden in sim TUs** (SimDeterminismLint), but this is render code, so it is permitted. State the side clearly in the dispatch spec to avoid the lint being mis-applied.
- The FieldGrid wind read is **one-way** (sim → render bridge, already frozen API); reading it does not affect the sim hash.
- The gate (`FoliageInstancing`) currently asserts an FNV-1a `instance_hash()` over CPU-side records. With generation moved to GPU there is no CPU instance set; **the gate must be re-pointed** at a deterministic surface that is cheap to read back (e.g. the indirect-args blade *count* per fixed input, plus a coverage probe), or kept as a CPU "shadow" evaluation of the same hash for the gate only. Call this out as an integration task.

## Integration notes (luminumbra files/systems touched)

- **`src/luminumbra_client/rendering/passes/FoliagePass.{h,cpp}`** — replaced/rewritten as the GPU grass pass. Keep `ChunkScatter` / `SurfaceQuery` host inputs and the `set_wind` / cloud-state uniforms; drop the CPU `rebuild_instances` scatter loop, the persistent-mapped 36 B instance ring, and `instances()`/`instance_hash()` read-backs (or keep a CPU shadow for the gate).
- **`res/shaders/foliage.vert` / `foliage.frag`** — replaced by `grass.comp` (layout+cull+append), `grass.vert` (Bézier blade from SSBO, indirect), `grass.frag` (scene-lit + analytic cloud shadow). The frag's existing `u_sun*`, `u_ambientColor`, and `u_cloud*` uniform set and the cloud projection math (FoliagePass.cpp:454-466) carry over verbatim.
- **`src/luminumbra_client/rendering/RenderPipeline.{h,cpp}`** — pass stays in the same slot (after aerial-perspective, before particle); reads the same scene depth and `m_lighting_pass->lighting_fbo()`; consumes `m_cloud_state` (`CloudRenderState`, RenderPipeline.h:148) and `m_sun` / `m_skyAmbientColor`. Per-pass GL timestamp timers already exist — wire the grass compute + draw spans in.
- **FieldGrid** (`src/luminumbra_common/fields/FieldGrid.h`, API frozen iter-6) — wind source via the existing one-way render bridge; no new consumer of the storage grid, just the sampled vector already passed to `set_wind`.
- **FarLodStore / FarLodSystem** (`src/luminumbra_common/world/FarLodStore.h`) — the *far-field texture-grass layer* (LOD tier 3) is baked into / sampled alongside the F1/F2 heightfield tiles drawn in the G-buffer; grass blades never spawn past the live ring, so the 64 MB FarLod budget is unaffected beyond a grass-tint contribution.
- **Materials LUT** (row 2, `kEmissiveLutScale = 8.0`) — grass albedo/emissive stays consistent with the lighting pass; Aetheric-emissive turf (if any) routes through the same LUT term.
- **Closes:** the foliage OPEN BLOCK and the `1/48 GREEN_SKY_SPECKLE` objective flag (continuous scene-lit turf replaces flat cross-quad cards that triggered the speckle/cyan defects).

## Open risks

1. **GoT's own grass ms/VRAM are unverified** — perf budget is a scaled third-party benchmark, not shipped numbers; must be re-measured on the engine's GL timers (quiet-machine baseline) before Wave A locks the shared GPU split.
2. **Gate re-point.** `FoliageInstancing` asserts a CPU instance hash that won't exist once generation is GPU-side; needs a new deterministic readback surface or a CPU shadow path, or the gate regresses to a no-op.
3. **Shared GPU budget contention.** 2.0 ms grass + SHIELD-RT raymarch + volumetric clouds + Aetheric sampling on one frame may exceed the total; Wave A must split explicitly and grass must degrade gracefully (lower ring count / earlier texture-grass handoff) under pressure.
4. **LOD pop / 4:1 thinning seams.** Pop-free transitions require the vertex-blend-at-boundary trick [1][3]; getting blade-count thinning to not visibly "shimmer" at the ring edge is the classic failure mode and where the visual-critique pipeline should focus.
5. **Cloud-shadow registration.** Grass must read the *identical* analytic cloud projection as the lighting pass; any drift (e.g. different scroll phase) reproduces the storm/teal mismatch. Share the exact `CloudRenderState` math, do not re-derive.
6. **GL feature baseline.** Compute + SSBO + indirect draw must be confirmed against the engine's GL context version (the GPUSDF compute path exists but is gated off — confirm it's a capability gate, not a hardware gap, before committing).
7. **Determinism lint mis-fire.** Compute shader uses transcendentals/atomics; ensure SimDeterminismLint scopes to sim TUs only and does not flag the render shader/host glue.
